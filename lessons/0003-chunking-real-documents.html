Chunking real documents

One win: turn a real 15-page PDF into chunks with page metadata, and see for yourself how chunk size decides what retrieval can find.

Why this next? In 0002, the chunks came pre-cut: one clean fact per line. Real documents arrive as messy PDFs. How you cut them is one of the biggest levers on RAG quality, and you can only see that by looking at the chunks.

2 · Knowledge: the three decisions in chunking

Loading: PDFs are lossy

A PDF stores where each character sits on the page, not paragraphs or tables. Text extraction rebuilds the reading order, and it gets things wrong: broken hyphenation, page headers in the middle of a sentence, tables flattened into number soup. Garbage in, garbage out: no chunking strategy can fix text that was extracted badly.

Size: a trade-off, not a magic number

Too smallToo large
A fact gets separated from what it's about ("h = 8" without "base model"). The vector is precise but missing context.Many topics get blended into one vector, so it matches everything weakly. It also wastes prompt tokens, and with them latency and money.

Chroma's evaluation found that ~200-token chunks gave the best precision, while recall stayed fairly similar across sizes. Overlap helped recall for small chunks but cost efficiency (Smith & Troynikov, Chroma, 2024). Their main advice, repeated elsewhere: always look at your data, and don't trust library defaults (Jason Liu with Anton Troynikov).

Splitter: recursive = respect structure

RecursiveCharacterTextSplitter tries to keep larger units (paragraphs) together, and only falls back to lines, then words, when a unit is too big (LangChain: Text splitters). chunk_size counts characters by default (Python's len), not tokens. Roughly, 1 token ≈ 4 English characters. chunk_overlap repeats the end of one chunk at the start of the next, so a fact that falls on a boundary still appears whole in at least one chunk.

Hidden limit: nomic-embed-text has a 2K-token context window (Ollama). Anything longer than that may be cut off without warning before it's embedded, so a huge chunk's later text never gets into its vector.

Metadata: the basis for citations

Each chunk is a Document(page_content=..., metadata={...}). The splitter copies the parent's metadata to every chunk, so if you record page at load time, every retrieved chunk can be cited as "page 5".

  2. Create labs\src\labs\003_chunking.py: 
    import math
from pathlib import Path
from urllib.request import urlretrieve

from langchain_core.documents import Document
from langchain_ollama import OllamaEmbeddings
from langchain_text_splitters import RecursiveCharacterTextSplitter
from pypdf import PdfReader

PDF = Path("data/attention.pdf")
if not PDF.exists():
    PDF.parent.mkdir(exist_ok=True)
    urlretrieve("https://arxiv.org/pdf/1706.03762", PDF)

# ---------- LOAD: one Document per page, page number kept as metadata ----------
reader = PdfReader(PDF)
pages = [
    Document(page_content=page.extract_text(), metadata={"source": PDF.name, "page": i + 1})
    for i, page in enumerate(reader.pages)
]
print(f"{len(pages)} pages, {sum(len(p.page_content) for p in pages):,} characters")

# ---------- CHUNK ----------
CHUNK_SIZE, OVERLAP = 1000, 200
splitter = RecursiveCharacterTextSplitter(chunk_size=CHUNK_SIZE, chunk_overlap=OVERLAP)
chunks = splitter.split_documents(pages)
print(f"{len(chunks)} chunks (size={CHUNK_SIZE}, overlap={OVERLAP})")

# ---------- EMBED + RETRIEVE (your 0002 code, now carrying Documents) ----------
embedder = OllamaEmbeddings(model="nomic-embed-text")
vectors = embedder.embed_documents([c.page_content for c in chunks])


def cosine(a, b):
    dot = sum(x * y for x, y in zip(a, b))
    norms = math.sqrt(sum(x * x for x in a)) * math.sqrt(sum(y * y for y in b))
    return dot / norms


def retrieve(question, k=3):
    q = embedder.embed_query(question)
    scored = [(cosine(q, vec), chunk) for chunk, vec in zip(chunks, vectors)]
    scored.sort(key=lambda s: s[0], reverse=True)  # Documents can't be compared, so sort by score only
    return scored[:k]


question = "How many attention heads does the base Transformer model use?"
for score, chunk in retrieve(question):
    print(f"\n--- {score:.3f} | page {chunk.metadata['page']} | {len(chunk.page_content)} chars")
    print(chunk.page_content[:400])
  3. Run it from labs\ with uv run src\labs\003_chunking.py. The PDF downloads into labs\data\ on the first run.

Ground truth for checking: the paper says the base model uses h = 8 heads (Section 3.2.2), and the big model scores 28.4 BLEU on English→German (abstract and Table 2). Knowing the right answer in advance is how you evaluate retrieval. Phase 3 scales this up into an eval set.

4 · Practice: predict, then run

a. Look before you chunk. Add print(pages[2].page_content[:1500]). What extraction damage do you expect?

What to look forWords split by hyphenation, equations turned into scattered symbols, figure labels mixed into the text, missing or extra line breaks. All of it gets embedded exactly as extracted. Production systems often use layout-aware parsers for this reason. We'll come back to it when we choose the capstone's data.

b. With 1000/200: is the "h = 8" chunk in the top 3? At what rank?

c. Change to CHUNK_SIZE, OVERLAP = 200, 0. Predict: how many chunks? Does "h = 8" still rank, and does the chunk still say what has 8 heads?

What you should seeRoughly 5× more chunks. The matching chunk may be tiny, and the number can end up cut off from "base model", or from the sentence that explains it. That's precise but missing context. Your rank and scores may differ from mine, and that's the point: you measure, you don't assume.

d. Now 4000, 0. Predict the top score compared with c, and how much irrelevant text you'd send to the LLM.

What you should seeFew chunks, each covering several topics. The right page probably still ranks high, but each retrieved chunk carries ~3,900 characters of unrelated text into the prompt. With k=3, that's ~12K characters of context to answer a question whose answer is one sentence.

e. Back to 1000/200. Ask "What BLEU score did the big model get on English-to-German?" Print a retrieved chunk that comes from Table 2 (page 8).

Why it mattersTables become rows of numbers without their column headers. The abstract states 28.4 in plain prose, so it may rank above the table, and that's fine. But in financial or technical documents the answer is often only in a table. Table handling is one of the hardest real-world RAG problems, and a good way to make your capstone stand out.
"I chose the chunk size empirically, not by default. I inspected the extracted text, tried a few sizes against questions with known answers, and kept page metadata on every chunk so the system can cite sources. Small chunks were more precise but lost context, large ones diluted the embedding and inflated prompt cost, which matches Chroma's chunking evaluation."
